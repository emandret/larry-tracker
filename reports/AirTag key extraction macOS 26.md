# Fix the fetch first, then free Larry's keys

As of 2026-10-26, **no method reads your AirTag's keys locally on a macOS 26 Mac**. The `findmy decrypt` failure is permanent on this machine, and so is every other on-device trick. Only two kinds of route still produce keys: an older Mac (macOS 14 or earlier) signed into your Apple ID, or an iCloud export tool that joins your iCloud Keychain over the network. The second kind is what bit you. stek29/export-findmy and OpenTagViewer's new in-app iCloud login are the only tools in that class, and export-findmy carries real account risk, as your run showed. A macOS VM does not help: macOS 14 guests cannot sign into iCloud, and a macOS 15+ guest has the same lockout as your Mac. A home-made OpenHaystack-style tag avoids key extraction entirely and works with larry-tracker's current `KeyPair.from_b64` code unchanged. Even so, **none of these routes delivers locations right now unless you also fix the separate fetch outage**. Since about 2026-10-12 Apple has withheld the `searchPartyToken` from the Android-style login that FindMy.py 0.10.2 and larry-tracker use, so every report fetch returns HTTP 401. Fix that first, whichever key route you pick.

## Every local route on this Mac is closed

Since macOS 15, the "BeaconStore" keychain key that decrypts Find My's accessory files can only be read by Apple-signed programs. Those programs carry a special keychain entitlement, `com.apple.icloud.searchpartyuseragent` ([beaconstorekey-extractor](https://github.com/pajowu/beaconstorekey-extractor)). Any other program is told the item does not exist, and that is exactly the error you got. The author of the widely used decrypt script wrote in early 2025 that "there is no known workaround for now" ([airy10 via YeapGuy gist](https://gist.github.com/YeapGuy/f473de53c2a4e8978bc63217359ca1e4)). FindMy.py's own compatibility table marks **macOS 14 as working, macOS 15 as needing a workaround, and macOS 26 as broken** ([FindMy.py #177](https://github.com/malmeloo/FindMy.py/issues/177)). A docs PR from August 2026 confirms that `python -m findmy decrypt` "no longer works" on macOS 26 ([FindMy.py PR #260](https://github.com/malmeloo/FindMy.py/pull/260)). On this Mac (macOS 26.6.2, build 25G83, SIP enabled), `security find-generic-password -l BeaconStore` returns "could not be found". The `~/Library/com.apple.icloud.searchpartyd/OwnedBeacons/` folder does not exist at all. So even a readable key would find no accessory records on this machine to decrypt.

The macOS 15 workaround does not carry over to macOS 26. On macOS 15 you could turn off SIP and AMFI (Apple's code-signing enforcement), lower the boot policy to Reduced Security, and run a self-signed binary that claims the entitlement ([beaconstorekey-extractor](https://github.com/pajowu/beaconstorekey-extractor)). The find-my-timeline project states flatly that **"on macOS 26 the SIP-disabling workaround no longer helps either"** ([find-my-timeline](https://github.com/liamschwie/find-my-timeline)). That is one project's assertion rather than a published failure log. Still, nobody reports success on macOS 26, and no LLDB or Frida memory-dump method aimed at this key has been published for any version. Weakening the Mac's boot security to chase an unproven exploit is a poor trade.

The VM idea fails at both ends. Apple's Virtualization framework allows an iCloud sign-in in a guest **only when both host and guest run macOS 15 or later**. A VM upgraded from an older macOS never gains that ability ([eclecticlight.co](https://eclecticlight.co/2026/04/29/virtualisation-on-apple-silicon-macs-is-different/); [Apple Developer Forums](https://developer.apple.com/forums/thread/707682)). A macOS 14 VM therefore never receives your Find My data. A macOS 15+ VM receives it but has the same entitlement lock as your Mac. Booting macOS 14 directly is also out. Your M4 MacBook Air (Mac16,12) shipped with macOS 15.3 as its minimum ([MacSales listing](https://eshop.macsales.com/item/Apple/KQ1HS33XXXXXB/)), and Apple Silicon Macs cannot run anything older than the release they shipped with. That floor comes from a reseller listing, not from Apple's spec page. **"Use an older Mac" therefore means a different, physical Mac on macOS 14 or earlier**, signed into your Apple ID, such as a friend's or family member's Intel or M1 to M3 machine that has not been upgraded. On such a Mac the old flow works. OpenTagViewer's export wizard also worked for one user on macOS 12.7.4 ([FindMy.py #177](https://github.com/malmeloo/FindMy.py/issues/177)). On macOS 11, the folder is called "MasterBeacons" and must be renamed to "OwnedBeacons".

## The iCloud export tools work for some, but they join your keychain

**stek29/export-findmy is the only open-source tool shown to export AirTag keys on macOS 26**, and it is a small, low-activity project. It signs into your Apple ID with 2FA, asks for a real device's passcode, and uses an escrow "bottle" to join your iCloud Keychain trust circle as a new synthetic device. It then downloads the encrypted BeaconStore records from CloudKit and writes FindMy.py-compatible `.json`/`.plist` files ([export-findmy](https://github.com/stek29/export-findmy)). The repo was last pushed on 2026-06-13. Its only pull request, #1, fixes macOS 26 by using the Mac's native anisette and correcting a client-info header. That PR has been **open, unmerged and uncommented since 2026-08-14** ([export-findmy PR #1](https://github.com/stek29/export-findmy/pull/1)). FindMy.py itself has no built-in export. Its maintainer calls the method "still a bit experimental and bound to change" and plans to integrate it "hopefully soon" ([PR #260](https://github.com/malmeloo/FindMy.py/pull/260)). As of today, the tracking issue is still open and no release after v0.10.2 (2026-09-14) has shipped ([FindMy.py #173](https://github.com/malmeloo/FindMy.py/issues/173)).

Your two failures fit what the code does. With the Mac's bottle, the error came **after** the escrow decryption had succeeded and the derived keys had matched. So your Mac password was accepted, and the `BadMsg` is a signature-verification mismatch inside rustpush. Its cause is unconfirmed, and nobody has reported it publicly. One plausible explanation is that newer macOS 26 escrow records changed in ways the fork does not track: the fork did not port upstream rustpush's switch to V2 authentication ([stek29 worklog](https://gist.github.com/stek29/4b15b02cf420223cc4c5b11e4870f5e0)). With the stale December 2024 iPhone bottle, the join succeeded. However, Octagon bottles hold only the device's own identity keys. The keychain zone keys arrive separately as "TLKShares" signed by other trusted devices ([Apple Security source](https://opensource.apple.com/source/Security/Security-59306.80.4/keychain/ot/OTClique.h.auto.html)). Your shares were signed by devices rustpush did not know, so the zone keys never unlocked and the tool reported "Decryption Key not found". **The library then tried to create new PCS keys in your iCloud Keychain, and panicked partway.** stek29's worklog confirms that this code path generates and wraps PCS master keys locally ([worklog](https://gist.github.com/stek29/4b15b02cf420223cc4c5b11e4870f5e0)). That is the most worrying behaviour of the tool. Writing freshly minted service keys into a real account could, in the worst case, conflict with the keys your iPhone and Mac use for Find My data. No public report shows that damage, but nobody has ruled it out either.

The worklog also shows that **each successful join commits a new bottle to your account, even if the run panics later** ([worklog](https://gist.github.com/stek29/4b15b02cf420223cc4c5b11e4870f5e0)). A read-only `otctl status` on your Mac shows the exporter's synthetic peer (serial F2LZN0FAKE00) listed as **excluded**, so it is no longer trusted. Your trusted peers are just the Mac and the iPhone, which is the state you want. You should still clean up. Run `--delete-own-escrow-bottle` to delete the exporter's own escrow bottle, and check the metadata carefully so you never delete a real device's bottle ([export-findmy](https://github.com/stek29/export-findmy)). Remove the fake device from your Apple ID device list if it appears there. Delete the tool's local state files (`keychain_state.plist` and anything else in its `.local` state). Those files hold trusted-peer material and should not sit on disk.

OpenTagViewer, an actively maintained Android viewer last pushed on 2026-10-23, now advertises reading keys "from iCloud, in the app (requires only your Android phone)" for tags the account owns ([OpenTagViewer](https://github.com/parawanderer/OpenTagViewer)). Its maintainer considers an iCloud route "the only proper long-term way to do it", because every OS-bound tool keeps breaking ([FindMy.py #177](https://github.com/malmeloo/FindMy.py/issues/177)). The research could not confirm how it works. If it also joins your keychain through an escrow bottle, the same attempt limit and side effects apply. AirPinpoint, a paid service at about $11.99 per device per month, reads keys locally on your own signed-in Mac with Full Disk Access, Xcode and a keychain prompt ([AirPinpoint docs](https://app.airpinpoint.com/docs/setup)). Its docs do not say it works on macOS 26, and it is closed source. Treat it as unproven for your setup.

## Refreshing the escrow bottle is possible but costs attempts

An escrow record is a copy of your keychain keys, protected by the device passcode or Mac login password and by an Apple hardware security module. **The HSM permanently destroys the record after 10 failed attempts**, and every wrong passcode typed into an export tool counts toward that limit ([Apple: escrow security](https://support.apple.com/guide/security/escrow-security-for-icloud-keychain-sec3e341e75d/web); [Apple: secure recovery](https://support.apple.com/guide/security/secure-icloud-keychain-recovery-secdeb202947/web)). Losing a record does not wipe the keychain on devices that already hold it, but it removes that recovery path. Apple's source code shows that new escrow records are requested mainly when trust is established or reset. **OS updates do not refresh the record**, which is why your iPhone runs a newer iOS but its record is still from build 22B91 (2024-12-09). There is no "re-escrow now" button. The likely triggers are changing the iPhone passcode to a new value, turning Passwords & Keychain sync off and on (which creates a new peer and bottle), or signing out of iCloud and back in. These are inferred from Apple's open-source Security code, not documented by Apple. Your earlier attempt did not change the iPhone's escrow date. If you do refresh it, confirm that the date changed before you run any tool again.

A refreshed bottle would most likely cure the "unknown sender" problem, because the new peer's view of the trust circle would be current. It would not cure the key-creation hazard, and it would not explain the Mac bottle's `BadMsg`. **Do not retry export-findmy unless you have counted your passcode attempts, use the PR #1 branch, and accept that the tool may write new keys into your iCloud Keychain.**

## The fetch outage breaks every route, including a DIY tag

Since about **2026-10-12**, a successful login returns only an `mmeAuthToken` from Apple's MobileMe service, with no `searchPartyToken`, and report fetches fail with HTTP 401. Users traced the cause to the anisette identity: logins that present an Android or Windows identity no longer get the token, while macOS and iOS identities still do. The issue was closed on 2026-10-25, and the maintainer remarked, "Apple finally did the thing I was afraid they'd do all along" ([FindMy.py #278](https://github.com/malmeloo/FindMy.py/issues/278); [macless-haystack #248](https://github.com/dchristl/macless-haystack/issues/248)). Two fixes have been confirmed by more than one user. The first is a real Mac's native anisette through AOSKit and PyObjC: one user had FindMy.py 0.10.2 fetching again on macOS 26.2 from 2026-10-22. The second is Apple's macOS CoreADI library, extracted from iTunes 12.8.3 and emulated on Linux, packaged as [sacca97/os-findmy-e](https://github.com/sacca97/os-findmy-e). The work to integrate a Mac anisette backend into FindMy.py is still **open as [FindMy.py #279](https://github.com/malmeloo/FindMy.py/issues/279)**, and no release includes it yet. Login has also churned in other ways. In September and October 2026 Apple returned 503 and `-80045` errors and changed how it signals 2FA ([macless-haystack #249](https://github.com/dchristl/macless-haystack/issues/249)).

This hits larry-tracker directly. `scripts/login.py` and the container both use FindMy.py's `LocalAnisetteProvider`, which is the Android-derived emulated library behind `/data/ani_libs.bin`. Your saved `account.json` was therefore minted with exactly the identity Apple now refuses. You have two options. You can run the location-service natively on the Mac with an AOSKit-backed provider, which is not Docker but is the most proven fix. Alternatively, you can add an os-findmy-e style macOS CoreADI anisette container and point `FINDMY_ANISETTE_SERVER_URL` at it, if its interface matches FindMy.py's remote provider. That compatibility was not verified. Either way you must re-run the login with the new provider, because a session is tied to the anisette identity that created it. Waiting for FindMy.py #279 to ship is the low-effort fallback. **None of the key routes above matters until this is fixed.**

## A DIY tag sidesteps extraction, at a reliability and courtesy cost

A self-made tag broadcasts a key that you generate yourself, so there is nothing to extract. FindMy.py's `KeyPair.new()` creates a P-224 key with a secure random generator. Its `private_key_b64` drops straight into `FINDMY_AIRTAG_KEY_B64`, and its `adv_key_b64` is what you flash onto the tag ([FindMy.py keys.py v0.10.2](https://github.com/malmeloo/FindMy.py/blob/v0.10.2/findmy/keys.py)). Prefer this over macless-haystack's `generate_keys.py`, which uses non-cryptographic `random.getrandbits()` ([macless-haystack #244](https://github.com/dchristl/macless-haystack/issues/244)). The only firmware project still releasing is **dchristl/macless-haystack, v2.7.2 from 2026-03-15**. Its nRF51 build has been tested on cheap AliExpress CR2032 beacons, including one in a "waterproof" case, while its nRF52 build is marked untested ([macless-haystack nrf5x](https://github.com/dchristl/macless-haystack/tree/main/firmware/nrf5x)). You also need an SWD programmer, such as a J-Link EDU Mini or an ST-Link clone, and the whole job costs roughly $0 to $50 ([Make:](https://makezine.com/projects/find-my-diy-airtag-tracker/)). Nobody has published measured battery life for this firmware. Generic nRF51 figures range from weeks to about a year, depending on the advertising interval ([Nordic DevZone](https://devzone.nordicsemi.com/f/nordic-q-a/11522/consumption-in-nrf51822)). Measure your own unit before trusting it on a cat, and use a breakaway collar.

The trade-offs are real. A DIY tag has no Precision Finding and no sound. Since September 2025, users have reported getting "less than half" the earlier number of location reports for DIY tags ([biemster/FindMy #88](https://github.com/biemster/FindMy/issues/88); [openhaystack #273](https://github.com/seemoo-lab/openhaystack/issues/273)). A single static key is also exactly what iPhones' "found moving with you" alerts recognise. Positive Security had to cycle 2,000 keys to avoid those alerts ([Positive Security, Find You](https://positive.security/blog/find-you)). A cat that stays near home seldom travels with a stranger, so the practical risk is probably low, but nobody has tested it on iOS 26. **Do not use key rotation or status-byte tricks to suppress alerts.** Those are stalking-evasion techniques. The tag adds no risk to your main Apple account, especially if you fetch with a secondary Apple ID, but it is still exposed to the anisette outage.

## What changes in larry-tracker for each route

If you go the DIY route, the service code needs **no changes at all**: it already calls `KeyPair.from_b64(settings.airtag_key_b64)` and `account.fetch_location_history(key)`. A real AirTag is different. It rotates its keys from a master key, so you must load the exported file as a `FindMyAccessory`, pass that object to the fetch call instead of a `KeyPair`, and replace the env var with a path to the accessory JSON on the `data/` volume. It is good practice to save the accessory back after each poll, the same way you save `account.json`, so that any updated key-alignment state persists. Several open issues from October 2026 report key-alignment problems with second-generation AirTags ([FindMy.py issues](https://github.com/malmeloo/FindMy.py/issues)). The exported AirTag file is as sensitive as `account.json`: anyone holding it can fetch Larry's location history, which in practice means your home address. Keep it in the gitignored `data/` volume. The research did not verify, line by line, that FindMy.py 0.10.2 loads export-findmy's or OpenTagViewer's output without conversion.

## Conclusion

The way to get AirTag keys has changed. A local keychain read used to be the standard method. Now the only routes are a network join of your iCloud Keychain or a still-working pre-macOS-15 machine. Meanwhile, Apple has started tying Find My data access to genuine Apple device identities. Both shifts point the same way. FindMy.py's maintainer and OpenTagViewer are moving toward iCloud-based export and macOS-style anisette, and larry-tracker's "Linux container with Android anisette" design is now the part most at odds with where Apple is heading. The durable fix is architectural: give the service a macOS-grade anisette source and plan for a re-login whenever Apple changes the rules again.

For Larry specifically, the cheapest safe path is a borrowed macOS 14 Mac for a one-time key export, which you only need once per tag ([FindMy.py #177](https://github.com/malmeloo/FindMy.py/issues/177)), plus the anisette fix. A DIY tag is the dependable backup that keeps your main account out of it entirely. Every further escrow experiment spends one of 10 attempts that cannot be reset, against a tool whose worst-case side effect lands on your real iCloud Keychain.
